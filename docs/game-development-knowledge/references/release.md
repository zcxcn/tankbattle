# 发布与交付

## 导出是独立的一次完整操作

相关实现和验证稳定后再导出；期间冻结会进入产物的源码和资源。后续若修改，复查受影响部分并重新导出，不复用旧包的验证结论。已有相关验证时可使用项目支持的跳过重复测试选项，但保留成品启动和完整性检查。

使用项目固定的引擎与匹配模板，核验可执行文件、模板和资源真实存在。不重复下载已有工具，也不把一次 Mac 临时导出变成所有后续改动的必做步骤。

检查版本在程序元数据、启动标记、UI、构建脚本、文件名和说明中的一致性。资源外置时保留数据包及署名；从导出后的可执行文件启动，不能只运行编辑器里的源项目。

交付记录包括文件路径、版本、架构、字节数、哈希和本次验证范围。工作缓存、原始转换临时文件、测试存档与账号数据不进入发行包。

## Windows 与 macOS 的常见边界

Windows 在其他命令前保存原生程序的退出码，同时检查 Godot/Blender 日志中的脚本错误与完成标记。打包清理限定在已核验的输出目录，不跨 shell 拼接递归删除操作。

Mac 导出先查看目标版本提供的模板架构，不能仅把配置改成 arm64 就假定存在对应模板。包中是否含 arm64、是否原生执行、是否使用兼容层，应由二进制与目标设备验证决定。

在 Windows 操作 `.app` 的 ZIP 时保留 Unix 执行位、符号链接和签名覆盖内容；普通解压再压缩可能破坏这些信息。附加说明和清单尽量放在已签名 app 外，修改 app 内容需要重新签名与验证。

跨平台静态检查可验证架构、资源、权限及签名结构，不能证明目标 Mac/Gatekeeper 已运行成功。明确未完成的实机检查；不通过关闭系统全局安全机制来让未验证产物“通过”。发布要求和官方模板行为随版本核实。

## 提交、上传与传文件

遵循当前项目已授权的提交/推送范围和提交身份。不要把某项目的匿名身份或既有授权写成全局默认；不伪装成具体真人。提交后确认 author/committer，推送结束后比对远端 SHA。

仓库提交、ZIP 打包、Release 上传和网站部署是不同动作。一个已忽略的本地 ZIP 不会随着 `git push` 自动公开；只报告真正完成的步骤。

远程桌面传文件时，文本剪贴板可用不代表文件剪贴板可用；把路径写入 FileDrop 也不代表接收端已收到。`\\tsclient\` 不存在仅表明当前会话无可访问映射，不能独自断言客户端没有配置。

重连多次仍失败时分层核查客户端文件夹权限、服务/策略与当前会话重定向，或改用用户已授权的传输渠道。注册表值改变不能证明握手已成功，不循环重复同一句建议。普通游戏开发不需要修改远程桌面服务、重启主机或注销用户。

压缩包完整传到目标设备后再解压；只有目标文件存在、校验成功或用户确认收到，才报告传输完成。
