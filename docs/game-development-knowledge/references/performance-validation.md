# 性能与验证

## 卡顿先分类型

先区分持续低帧率、偶发长帧、首次加载/着色器编译，以及远程桌面/窗口呈现受限。记录场景、镜头、敌人数量、画质、设备与采样区间；比较 CPU、GPU、物理、节点/绘制数量和资源分配，不用一次截图左上角 FPS 推断根因。

优化比较使用相同场景、种子、输入和预热条件；测量时避免同时导入素材、运行其他全量测试或转换模型。平均帧率可能掩盖偶发停顿，观察长帧和分位数，并区分局部函数耗时与整帧耗时。

曾出现远程截图中新地图 1–2 FPS、旧地图对照也约 1 FPS 的情况。它不足以定位具体系统原因，更不能证明新地图无性能问题；应换可测量的前台条件或采集更细的时间数据，不立刻降低画质或宣称已有性能提升。

## 优先消除重复工作

| 常见热点 | 可验证的改法 |
| --- | --- |
| 死亡时逐顶点/逐骨骼重算 | 按共享 mesh/skin 缓存真正有权重的变形骨骼；进入战斗前预热，死亡时仅取当前姿势 |
| 隐藏菜单每帧刷新布局 | 仅在显示或相关数据变化时刷新，HUD 保持所需实时性 |
| 大量静态装饰节点 | 共享资源、静态合批或空间分块实例化，保留合理裁剪粒度 |
| 每帧重复搜索/邻居扫描 | 复用查询结果或分时更新，保留攻击和近距离碰撞准确性 |
| 每次事件即时导入/构造重资产 | 缓存已加载资源；只有测得频繁分配回收代价时才引入对象池 |
| 重复写未变化的材质/天气状态 | 缓存状态，在事件发生时更新；注意新建材质也需要初始化 |

这些是排查方向，先测量再应用。不能为了优化把近景细节、特效层次或声音尾部一刀切掉；模型 LOD、距离更新等取舍应经过实际画面比较。

## 与修改匹配的最小验证集

- 参数或 AI：真实感知、移动、开火、命中和遮挡；同时查玩法节奏。
- 波次或进度：生产主循环、队列/活体边界、暂停、失败、重试和重复结算。
- 地形或大体型：真实物理通行、完整包围体、坡面、桥口、出生净空与相机。
- 模型或动画：实际引擎导入、骨骼变化、比例、近远景、死亡姿态与贴图。
- 声音或镜头：事件调用加实际输出检查，覆盖设备/远程输入的限制。
- 文档：路径、引用、事实与差异；无需重建游戏。

测试沿用生产代码，隔离存档/设置，固定随机种子以复现，保留必要的时间行为。Godot 固定 FPS 快进不适合所有测试：模拟计时器可能在真实音频线程退出前超时。验证退出码、错误日志、断言汇总和完成标记，不能只看“有 PASS”或窗口成功打开。

修复前有稳定复现，修复后让同一路径通过。避免测试只断言刚写入的配置值；也避免为了得到通过而强行开火、清空敌人或直接调用下一波，跳过用户遇到的流程。

## 截图和证据边界

等本轮捕获完成，核对文件时间；同名旧截图不能证明新修改。冻结游戏进程拍照时先更新 UI 快照，否则可能把已开战的画面配上旧主菜单。观察正常视角，而不只拍漂亮的自由相机镜头。

“已实现”“相关测试通过”“实际渲染/听过”“成品启动通过”“目标设备实测”“已上传”分开记录。当前修改只引用当前证据；历史通过数和局部毫秒优化不能变成整局性能承诺。
