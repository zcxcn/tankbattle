# 工作流与架构

## 接手项目：用最少读取建立地图

先确认工作区改动、当前分支、目标平台、引擎版本与现有启动/构建命令。优先查项目约定和入口函数，再沿调用链读取局部代码。不要默认切历史分支、递归搜索整个用户目录，或把完整源码与历史日志塞进上下文。

分开辨认客户端：网页、原生 PC、移动端可以是不同实现。请求“重做成专业 PC 游戏”时，先确认用户要的是原生引擎实现还是现有程序封装；不能用外壳代替重制，也不能顺手改所有客户端。

“继续”应承接已有未完成工作。交接记录写明已验证的文件、剩余问题和下一步，不重新调研已经确认的工具与决定。

## 新项目选型：先验证约束，再承诺

保留已有引擎通常比迁移更便宜；仅在当前目标确有障碍时评估迁移。Godot、Unity、Unreal 或浏览器方案的取舍，依据团队熟悉度、目标平台、图形要求、内容规模、插件依赖、许可和发行流程，不给出脱离项目的“最快、最稳、最真实”排名。

用一个小型可玩片段检查：输入 → 镜头 → 一个敌人 → 攻击/命中 → 反馈 → 胜负 → 目标平台导出。确认模型导入、阴影/透明材质、最低配置和打包可行后再扩内容。原生引擎并不会自动让低质量模型、音效和战斗节奏变好。

版本从现有构建脚本与工具读取，核实文件确实存在；升级引擎前评估模板、导入器、API 和目标设备的兼容，不因为发现新版本就升级。涉及当前产品能力、许可和平台支持时查官方来源。

## 模块边界服务于可玩行为

| 责任 | 建议边界 |
| --- | --- |
| 玩法状态与关卡切换 | 唯一的流程管理入口，负责创建与清理 |
| 角色、载具、投射物 | 各自移动、命中与生命周期，避免反向掌管全局关卡 |
| 波次与生成 | 调度器维护待生成、在场活体、生成失败及推进条件 |
| 武器、敌人、任务参数 | 数据定义，避免同一数值散落在 HUD、角色与关卡中 |
| UI、音频、镜头 | 消费明确状态/事件，避免反过来决定伤害与奖励 |
| 存档与设置 | 进度、单局数据、设备偏好分开，测试使用独立目录 |

不为简单改动一次性拆出全部模块。新增功能沿用现有可测试入口，只有实际耦合妨碍工作时才调整边界。

## 一次迭代的可核验结果

把“更真实”“更好玩”转成玩家可感知的目标，例如能看见炮口闪光、可以判断来弹方向、敌人有反应时间、山坡确实可驾驶。记录触发条件、原行为、预期行为和一条验证路径；先形成可玩结果，再扩大种类与细节。

源码变化与发布分阶段：实现/相关验证 → 视觉或听觉检查 → 稳定后导出。不要在导出期间继续修改会进入成品的文件。
